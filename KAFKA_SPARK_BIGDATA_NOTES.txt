================================================================================
BTMS - BIG DATA, KAFKA & SPARK IMPLEMENTATION NOTES
AI-Enabled Battery Thermal Management System
================================================================================

1. OVERVIEW
-----------
The BTMS simulates telemetry from a pack of ten 21700 Li-ion cells and
processes it as a real-time data stream. Redis was replaced by Apache Kafka
as the message backbone, and a big-data analytics layer (Spark Structured
Streaming + Parquet data lake + analytics API) was added on top.

Data flow:

  Simulator --HTTP--> Ingestion (Flask) --produce--> Kafka topic battery_stream
                                                        |
        +-----------------------------------------------+---------------+
        |                                                               |
  AI Engine (consumer group btms-ai-engine)            Spark Structured Streaming
   - IsolationForest ML anomaly detection               (reads battery_stream)
   - CFD coolant optimisation                            |
   - publishes events:                                   v
        btms_recommendations (every tick)           Parquet data lake
        btms_alerts          (anomalies only)       raw / cell_metrics / pack_metrics
        |                                                |
        v                                                v
  Alert Service (consumer group btms-alert-service)  Analytics API (pandas + PyArrow)
   - stores alerts in SQLite, REST API                   |
                                                         v
                                                  React /analytics page

  Kafka UI (provectus) is attached to the broker to inspect topics and lag.


2. APACHE KAFKA - WHAT WAS IMPLEMENTED
--------------------------------------
2.1 Broker (docker-compose.yml, service "message-broker")
  - Image apache/kafka:3.8.0, single node running in KRaft mode
    (broker + controller in one process, no Zookeeper).
  - Two listeners: INTERNAL (message-broker:19092) for containers and
    EXTERNAL (localhost:9092) for the host machine; this is the advertised-
    listeners pattern needed so both Docker clients and host clients work.
  - Auto topic creation enabled; log retention 10 minutes
    (KAFKA_LOG_RETENTION_MS=600000); replication factor 1 (single broker).
  - Healthcheck uses kafka-broker-api-versions.sh; dependent services wait
    for service_healthy.

2.2 Topics
  - battery_stream        raw telemetry (producer: ingestion)
  - btms_recommendations  one event per processed tick (producer: AI engine)
  - btms_alerts           events for detected anomalies (producer: AI engine)

2.3 Producers (confluent-kafka 2.5.0)
  - Ingestion service (ingestion/app.py): lazily creates a Producer, publishes
    the normalised JSON payload keyed "btms-pack" (a constant key keeps all
    ticks in one partition, preserving order), linger.ms=5 for micro-batching,
    asynchronous produce() + poll(0), message.timeout.ms=5000.
  - /health on ingestion checks broker reachability via list_topics().
  - AI engine (ai_engine/main.py): publish_event() helper that publishes
    recommendation and alert events; failures are logged and never block the
    consumer loop. JSON serialisation handles numpy types.

2.4 Consumers and consumer groups
  - AI engine: group "btms-ai-engine", auto.offset.reset=latest,
    enable.auto.commit=true, poll loop with 2 s timeout, reconnect on error.
  - Alert service: group "btms-alert-service", auto.offset.reset=earliest,
    so alerts published before it connected are not lost.
  - Spark: its own internal Kafka consumer (subscribe=battery_stream).
  - Because each consumer uses a different group, all of them receive every
    message independently (publish/subscribe fan-out), unlike the old Redis
    list queue where a message was removed after one consumer popped it.

2.5 Event-driven architecture
  - The AI engine publishes downstream events and the Alert Service reacts to
    them, so services are decoupled and communicate only through topics.
  - Alert Service (alert_service/main.py): background consumer thread ->
    SQLite table "alerts" (stores Kafka partition and offset with each row) ->
    REST endpoints GET /alerts, GET /alerts/stats, GET /health.

2.6 Operations tooling
  - Kafka UI container (http://localhost:8080) to browse topics, partitions,
    messages, consumer groups and consumer lag.

2.7 Behavioural differences vs Redis (previous design)
  - Redis: bounded in-memory list (LPUSH/LTRIM/BRPOP), message consumed once,
    last 200 kept.
  - Kafka: durable, replayable append-only log with time-based retention,
    multiple independent consumers, offsets tracked per consumer group.


3. APACHE SPARK - WHAT WAS IMPLEMENTED
--------------------------------------
File: analytics/spark_job.py (PySpark 3.5.1, Spark Structured Streaming).
Runs in its own container (needs Java; the Kafka connector package
org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.1 is fetched at startup).

3.1 Source and parsing
  - readStream from Kafka (startingOffsets=latest, failOnDataLoss=false).
  - from_json() with an explicit schema (StructType/ArrayType) to parse the
    telemetry JSON (tick, timestamp, pack_id, cells[]).
  - explode() flattens the cells array: one row per cell reading.
  - Event time = payload timestamp, falling back to the Kafka message
    timestamp (coalesce).

3.2 Three-layer data lake ("medallion" architecture) stored as Parquet
  - Bronze  lake/raw/           every reading, partitioned by date.
  - Silver  lake/cell_metrics/  per-cell stats over 30 s SLIDING windows
            (10 s slide): avg/min/max/stddev temperature, avg voltage,
            current, SoC, spike count, sample count.
  - Gold    lake/pack_metrics/  pack-level 10 s TUMBLING windows: Tmax, Tmin,
            Tavg, delta-T (Tmax-Tmin), spike readings, spiking-cell count.

3.3 Streaming concepts used
  - Micro-batch processing with processingTime trigger (10 s).
  - Event-time windowing: tumbling and sliding windows.
  - Watermarking (10 s) to bound state and decide when a window is final.
  - Append output mode (each window written once after it closes).
  - Checkpointing (lake/_checkpoints) for fault tolerance / exactly-once
    file sink semantics and restart recovery.
  - Multiple concurrent streaming queries in one application
    (awaitAnyTermination).
  - Stateful aggregations (groupBy window).
  - Lesson learned: exact distinct aggregation (countDistinct) is not
    supported on streaming data, so approx_count_distinct (HyperLogLog) is
    used for the spiking-cell count.


4. ANALYTICS API (batch-style analytics over the lake)
------------------------------------------------------
File: analytics/api.py (FastAPI + pandas + PyArrow), port 8100, reads the
Parquet lake (read-only volume mount).
  /summary      readings, ticks, spike rate, mean, P95/P99 temperature,
                mean/P95 delta-T, delta-T < 5 C compliance %, hottest and
                coolest cell, mean SoC.
  /pack-trend   10 s window time series from the Gold layer.
  /cells        per-cell mean, std dev, P95, max, spike rate, plus a composite
                thermal-risk score (50% spike rate, 35% P95 temp, 15% variance)
                and ranking.
  /correlation  Pearson correlation matrix (temperature, voltage, current, SoC).
  /distribution temperature histogram.
  /anomalies    recent windows with a spike or delta-T >= 5 C.
  /health       file counts per lake layer.

React dashboard page /analytics (dashboard/src/pages/AnalyticsPage.jsx)
visualises all of the above: KPI cards, window trend chart, histogram, risk
ranking table, correlation heatmap, anomalous windows, lake file counts.
nginx and the Vite dev server proxy /analytics-api to the API.


5. AI / ML COMPONENT (consumes the stream)
------------------------------------------
  - IsolationForest (scikit-learn) unsupervised anomaly detector on an
    8-feature vector per cell, bootstrapped on synthetic data and retrained on
    a rolling buffer of live data (online/continuous learning).
  - CFD heuristic model (Reynolds number, Dittus-Boelter, nanofluid
    Al2O3/water properties) turns the ML severity into coolant flow-rate and
    nanoparticle-concentration recommendations.


6. BIG DATA CONCEPTS USED (GLOSSARY)
------------------------------------
  - Stream processing / real-time analytics: continuous processing of
    unbounded telemetry rather than periodic batch jobs.
  - Publish/subscribe messaging and decoupling of producers and consumers.
  - Distributed commit log: Kafka topics as durable, ordered, replayable logs.
  - Topics, partitions, message keys and ordering guarantees (per partition).
  - Offsets and consumer groups; independent consumption by multiple groups.
  - Retention policy (time-based) vs. queue semantics.
  - Replication factor (1 here; production would use >= 3).
  - KRaft consensus mode (metadata managed by Kafka itself, no Zookeeper).
  - Listener / advertised-listener networking in containers.
  - Producer batching (linger.ms), async delivery, delivery timeouts.
  - At-least-once consumption with auto-commit.
  - Event-driven / event-sourcing style architecture (events on topics).
  - Micro-batch streaming (Spark Structured Streaming).
  - Event time vs processing time; watermarks and late data handling.
  - Tumbling and sliding windows; windowed and stateful aggregation.
  - Checkpointing and fault-tolerant recovery.
  - Schema-on-read with an explicit schema for semi-structured JSON.
  - Data flattening (explode of nested arrays).
  - Columnar storage: Apache Parquet; partitioning by date (partition
    pruning); compression and efficient column reads via PyArrow.
  - Data lake and medallion (bronze / silver / gold) layering.
  - Pre-aggregation (rollups) vs raw data access.
  - Approximate algorithms: HyperLogLog (approx_count_distinct).
  - Descriptive statistics at scale: mean, standard deviation, percentiles
    (P95/P99), histograms, correlation matrix.
  - Anomaly detection (unsupervised ML, Isolation Forest) on streaming data.
  - Composite scoring / ranking (thermal-risk score).
  - Microservices, containerisation and orchestration (Docker Compose),
    shared volumes for the lake, health checks and startup dependencies.
  - Observability: Kafka UI for topic inspection and consumer lag.
  - Polyglot persistence: Kafka (stream), Parquet (analytics), SQLite
    (alerts and users).

9. KNOWN LIMITATIONS / NOTES
----------------------------
  - Single Kafka broker, replication factor 1, one partition per topic by
    default (auto-created); not production-grade HA.
  - Auto-commit consumers give at-least-once, not exactly-once, semantics.
  - Spark starts from the latest offset; it does not backfill history.
  - First Spark start downloads the Kafka connector (needs internet).
  - The alert path (btms_alerts -> alert-service) was deployed but an alert
    being stored end to end was not yet confirmed at the time of writing.
  - Simulator spikes make delta-T < 5 C compliance near 0% (simulation
    artefact, not a pipeline fault).
  - Ideas not implemented: dead-letter topic, multi-partition scaling with
    several AI engine replicas, Schema Registry (Avro), Kafka Connect,
    SSE/WebSocket push from Kafka to the dashboard.
